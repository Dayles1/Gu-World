# Генератор горы Цинмао: как устроен, как запускать, ограничения

Код: `Assets/GuWorld/Editor/World/`. Всё, что генератор создаёт, лежит в
`Assets/GuWorld/Locations/QingMao/Generated/` — эта папка не в git, её можно собрать заново.
Материалы и текстуры (`Locations/QingMao/Materials`, `Textures`) — в git.

## 1. Сбой сборки 11.10.2026

**Что было.** Сборка шла одним заходом, одним процессом Unity и одной сценой. За 13 минут
она успела сделать:
- 21:19–21:22 — планы деревень и тропы;
- 21:22–21:25 — 16 тайлов основного рельефа;
- 21:25–21:30 — точные тайлы Гу Юэ, Сюн и Бай;
- 21:30–21:32 — меши троп, ручьёв, первых домов Гу Юэ.

Около 21:32 Claude Code остановил процесс: в системе кончалась оперативная память.

**Доказательства** (журнал `qm.log` той сборки и файлы на диске):
- ошибок и исключений Unity в журнале нет. Последние строки — обычный импорт ассетов,
  обрыв без сообщения. Значит, процесс убили снаружи, а не упал код;
- все 19 файлов террейнов (`Generated/Terrain/*.asset`) весят по 8.7 КБ: это пустые
  заготовки без высот. Сборка ни разу не сохранила ассеты на диск, и все 19 террейнов со
  всеми данными держались в памяти до конца;
- в `Generated/Meshes` 836 недоделанных мешей (88 МБ), сцена не сохранена;
- память самого Unity в журнал не писалась, поэтому точный пик неизвестен. Сейчас в системе
  при обычной работе (Chrome, VS Code, Telegram) свободно около 6 ГБ из 15.7 ГБ: этот
  запас Unity и выбрал.

**Что не пострадало.** Тестовая сцена `Assets/GuWorld/Scenes/TestGrounds.unity` в git
без изменений. Старая карта (три холма) удалена из рабочей копии, но хранится в git: тег
`backup/qingmao-three-hills` (коммит 89e3b37). Незакоммиченный код переработки сохранён
снимком в ветке `wip/qingmao-rework-snapshot`, рабочая копия при этом не менялась.

**Что можно переиспользовать.** Ничего. Террейны пустые, недоделанные меши устарели, и
генератор детерминирован: то же самое получается пересборкой. Папку `Generated` можно
спокойно очищать.

## 2. Почему сборка держала столько памяти

Подтверждено по коду:
1. **Одна сцена на всё.** Террейны, все деревни, тропы, деревья — всё создавалось в одной
   открытой сцене до самого конца. Unity не может выгрузить то, на что ссылается сцена,
   так что память только росла.
2. **Ничего не сохранялось по ходу.** `AssetDatabase.SaveAssets` вызывался один раз в
   конце, и все созданные меши и террейны жили в памяти как несохранённые объекты.
3. **Временные массивы покраски.** Покраска точного тайла Гу Юэ —
   `float[2048, 2048, 8]` = 134 МБ одним массивом (уже уменьшено до 1024: 33 МБ).
4. **Кэш мешей `built`** держал ссылки на все сделанные меши до конца сборки.
5. **Сборщики мешей (MeshKit) кварталов** хранят все вершины квартала в списках до его
   окончания. Для Гу Юэ это тысячи предметов.

Гипотезы, которые проверяет этап B (замеры — в [tests.md](tests.md)):
- деревья на террейнах: около 60 тыс. на тайл, около 1 млн на всю гору;
- коллайдеры (MeshCollider на ступенях и тропах);
- сохранение огромных иерархий (тысячи домов) в префаб или сцену.

## 3. Поэтапная сборка

Каждый этап начинается с пустой сцены, сохраняет свой результат и выгружает его.
Дальше остаются только планы деревень и тропы: они небольшие и нужны всем этапам.

| Этап | Что делает | Результат |
|---|---|---|
| `terrain` | 16 тайлов рельефа: высоты, дыры под деревни, покраска, трава, деревья. **По одному**: каждый сохраняется и выгружается | `Generated/Terrain/Mountain x-z.asset` |
| `fine` | точные тайлы трёх деревень и «юбки» по их краю | `Terrain/Village <id>.asset`, `Meshes/... Skirt` |
| `village-gu_yue`, `village-xiong`, `village-bai` | деревня по плану: дома, стены, лестницы, предметы, огни, дорожки жителей | `Parts/Village <id>.prefab` + `Stages/<этап>.plan.json` (дома, улицы, метки для карты) |
| `water` | ручьи, омут, водопад, брызги | `Parts/Water.prefab` |
| `trails` | ленты троп, каменные ступени, мосты. Стоит на загруженном рельефе | `Parts/Trails.prefab` |
| `hamlets` | хутора у подножия | `Parts/Hamlets.prefab` + план |
| `giants` | гигантские деревья с ветками | `Parts/Giant Trees.prefab` |
| `assemble` | сцена: рельеф, все части, окрестности, небо, игра, план мира. Перед записью старая сцена копируется в `QingMao (previous).unity` | `Generated/QingMao.unity` |

**Продолжение после сбоя.** Готовый этап оставляет метку `Generated/Stages/<этап>.done`
с временем, длительностью и пиком памяти. Тайлы рельефа отмечаются по одному. Запуск без
списка этапов делает только неготовые, то есть просто продолжает. Если этап собирается
заново, снимаются метки с зависящих от него: `trails`, `hamlets`, `giants` стоят на
рельефе, `assemble` — на всём.

**Стабильные GUID.** Меш, который уже есть на диске, не удаляется и не создаётся заново,
а перезаписывается на месте (`Keep`). Поэтому префаб одного этапа не ломается, когда другой
этап пересобирает общий меш.

**Детерминизм.** Сиды берутся из имён стабильным хешем (FNV-1a, `QingMaoBuilder.Seed`),
а не `string.GetHashCode`: в разных процессах Unity получаются одинаковые планы.

## 4. Как запускать

Только **один** тяжёлый Unity одновременно. Скрипт сам откажется стартовать, если Unity уже
запущен: закройте редактор.

```powershell
# всю гору (или продолжить после остановки)
powershell -ExecutionPolicy Bypass -File Tools\QingMao\build.ps1
# отдельные этапы заново
powershell -ExecutionPolicy Bypass -File Tools\QingMao\build.ps1 -Stages "village-gu_yue,assemble"
# тест на маленьком участке, в отдельную папку GeneratedTest
powershell -ExecutionPolicy Bypass -File Tools\QingMao\build.ps1 -Test -Area "-1960,6440,1400" -Stages "terrain,fine,village-bai,assemble"
```

`build.ps1` собирает все этапы, кроме сцены, в одном процессе Unity, а этап `assemble` —
в **отдельном свежем процессе**. За 12 минут память долгого процесса разрастается
(фрагментация), а сборке сцены нужна вся гора сразу. Один раз сборка сцены в том же процессе
остановилась при 1 ГБ свободной памяти; в свежем процессе её пик 3.1–3.5 ГБ.

Сторож (`build.ps1`) каждые 2 секунды проверяет память:
- все процессы Unity вместе заняли больше `-LimitMB` (по умолчанию 4500 МБ) — Unity
  останавливается;
- у системы осталось меньше `-MinFreeMB` свободной памяти (1500 МБ) — тоже остановка.

Причина остановки пишется в журнал. Сам сторож сборку не перезапускает.

Журналы в `Logs/QingMaoBuild/`:
- `progress.log` — строка на каждый шаг генератора, с памятью. Последняя строка показывает,
  где остановилось;
- `guard.log` — память раз в 30 секунд и причина остановки;
- `unity-*.log` — журнал самого Unity.

Из редактора: меню **Gu World → Build Qing Mao Mountain** (неготовые этапы) или
**… (every stage again)** (все этапы заново).

**Что делает сторож помимо замера.** Как только генератор начал работу, сторож останавливает
простаивающие процессы Unity:
- импортёр ассетов `AssetImportWorker` — отдельный Unity, 1.4 ГБ;
- сервер компилятора (dotnet/VBCSCompiler) — до 1.2 ГБ.

Без этого на 16 ГБ памяти не хватало. Для тестов в play mode (`RouteWalk`) есть ключ
`-NoQuit`, для ограничения по времени — `-TimeoutMinutes`.

## 5. Ограничения генератора

- Основной рельеф — 16 тайлов по 5 км, шаг сетки 4.9 м. Мелкие скалы и уступы на нём
  грубые. Подробно (шаг 0.61 м) только участки деревень: Гу Юэ 1250 м, Сюн и Бай по 625 м.
- Стык точного тайла с основным выравнивается по полосе 30 м по краю и закрывается
  «юбкой». Вдали, при смене уровня детализации, на стыке может мелькать щель.
- Деревни, тропы и ручьи генерируются, а не ставятся вручную. Чтобы поправить место,
  меняют параметры (`QingMao.cs`, `MountainShape.cs`) и пересобирают.
- Изменения формы рельефа (`MountainShape`) требуют пересобрать все этапы.
